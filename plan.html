Architecture & build plan

Phases, Not Slides

A scroll-driven presentation studio: one continuous scroll axis, components that move, rotate, and scale independently through it, authored in natural language and stored as plain files.

draft v0.1 2026-10-07 css transforms only — no webgl

01

Concept

A slide deck forces every idea into identically-shaped containers that all change at once. This tool treats a presentation as a single scroll track, divided into named phases, where every component carries its own path through space — independent of its neighbors. The same scroll gesture that advances the narrative also drives the choreography.

Phases, not slides
A presentation is one continuous scroll track. Phases are named destinations along it — markers for navigation, snapping, and export — not containers that own the motion itself.
Independent choreography
Every component carries its own keyframe path through absolute scroll position — waypoints placed wherever that component needs them, not snapped to phase boundaries. Nothing is required to enter, exit, or move in lockstep with anything else.
Presentation as code
Each presentation is a folder on disk: component source files, one config file, and an assets folder. Legible, diffable, and git-friendly by construction.

02

Data model: the presentation folder

Every presentation is a self-contained directory. Nothing lives in a database — the folder is the presentation.

workspace/presentations/quarterly-vision/ 
quarterly-vision/
├── presentation.json       # metadata, phases, keyframes
├── components/
│   ├── hero-title.tsx
│   ├── revenue-chart.tsx
│   └── team-photo.tsx
└── assets/
    ├── logo.png
    └── team-photo.jpg

presentation.json is the single source of truth, validated against a Zod schema shared by the editor, the runtime, and the AI panel's write path:

presentation.jsonabbreviated 
{
  "meta": { "title": "Quarterly Vision", "aspectRatio": "16:9" },
  "phases": [
    { "id": "intro",  "label": "Intro",  "duration": 1200 },
    { "id": "growth", "label": "Growth", "duration": 1800 }
  ],
  "components": [
    {
      "id": "hero-title",
      "file": "components/hero-title.tsx",
      "keyframes": [
        { "at": 0,    "x": 0,    "z": 0,   "scale": 1,    "opacity": 1 },
        { "at": 900,  "x": -180, "z": -30, "scale": 0.85, "opacity": 0.8 },
        { "at": 1600, "x": -400, "z": -80, "scale": 0.6,  "opacity": 0.4 }
      ]
    }
  ]
}

at is an absolute offset along the whole scroll track, in the same units as phase.duration — not a phase id. A keyframe can land in the middle of a phase, right on a boundary, or anywhere else; a component can have as many or as few as it needs, and the schema just requires them sorted by at.

A phase's own start offset is just the sum of every earlier phase's duration, so phases lay out end-to-end along the same axis with no gaps. That start offset is exactly the point every component's inbound motion has finished settling into — which is the offset present-mode snapping and PDF export (§06–§07) both lock onto.

Two rules follow directly from this shape. First, scroll offset is the only input the engine ever reads — phases are named ranges layered on top of that same axis for navigation, present-mode snapping, and PDF page breaks, but they hold no motion data of their own. Second, a component holds its last keyframe's value past it, and interpolates between its two surrounding keyframes everywhere else — which is what lets one component sit still for an entire phase while another runs through three keyframes in a few hundred pixels.

03

Scroll & animation engine

The engine reads exactly one input: the raw scroll offset. Each component independently looks up its own keyframe array for the two keyframes bracketing the current offset and interpolates between them — phase boundaries never enter that calculation. A separate, much lighter lookup maps the same raw offset to "which phase is active," purely for UI concerns: a progress indicator, a present-mode label, a highlighted row in the editor's timeline. That lookup has no influence on how any component actually moves.

Two constraints keep this fast and keep it feeling spatial rather than flat:

  • Transforms are applied as translate3d / rotate / scale and opacity only — never top/left — so every change stays on the GPU-accelerated compositing path.
  • Scroll state lives in a selector-based store (Zustand/Jotai), so a scroll tick re-renders only the components whose computed transform actually changed — not the whole tree. With dozens of independently-animating components, this is the difference between smooth and unusable.
  • The stage container uses CSS perspective + transform-style: preserve-3d, so rotateX/Y/Z and translateZ read as genuine depth — real spatial motion without a WebGL canvas.

04

The AI generation panel

Natural-language authoring is built into the app, not bolted on through an external CLI. A server function calls the Claude API directly and runs a small, deliberately scoped tool-use loop: read_file, list_files, write_component, propose_keyframes — every tool constrained to that one presentation's folder.

Every component the panel writes is held to a fixed authoring contract, enforced in the system prompt and checked before anything touches disk:

  • Default-exports a React component that accepts one style prop — the already-resolved transform and opacity. A component never reads scroll position itself.
  • Styled with Tailwind, which the model generates far more reliably than ad-hoc CSS.
  • Self-contained — no implicit dependency on sibling components.

Proposed changes — new files, edited files, keyframe updates — surface as a diff for approval before they're committed to the folder, the same trust model Claude Code uses for file edits. The config schema validates the result either way, so a bad generation can't silently corrupt presentation.json.

05

Editor mode

A canvas shows whatever the current scroll offset renders. A timeline at the bottom scrubs along that same absolute scroll axis like a video editor's playhead, with phase ranges drawn as labeled bands behind it. Each component gets its own row, its keyframes drawn as diamonds at their real offsets — free to land anywhere, inside one phase or spanning several. A sidebar lists components; a properties panel edits the selected component's nearest keyframe numerically. Dragging a component on the canvas moves its nearest keyframe, or inserts a new one at the exact scrub position if none is close enough. The natural-language panel from §04 docks alongside as a fourth way to make the same edits.

06

Present / preview mode

The same engine, full-screen, driven by real wheel/trackpad/touch scrolling. An optional snap-to-phase mode makes it behave like a deck again when presenting live — click or arrow-key to the next phase's start offset instead of scrolling freely, landing on exactly the resting position §07 also captures for export. Speaker-facing affordances (phase labels, elapsed progress, notes) are a v2 concern, not required to validate the core idea.

07

PDF export

Each phase's start becomes one PDF page. A phase's start offset (§02) is, by construction, the moment every component has finished arriving — the last keyframe any of them needed to reach has already passed, so what's on screen is a settled composition rather than something mid-flight. That's the "slide" worth capturing.

A dedicated static route locks scroll directly to a given phase's start offset and lets the ordinary engine compute every component's transform from its own keyframes — there's no separate "phase snapshot" to store or let drift out of sync. Headless Chromium (Playwright) screenshots that route once per phase at high resolution, in phase order; the images are composed into a PDF with pdf-lib.

Screenshots over vector output, deliberately: fidelity to exactly what's on screen matters more here than file size, and raster degrades gracefully if a component ever gets visually more complex than plain CSS.

08

Tech stack

Layer Choice Why
App shell TanStack Start + Router Full-stack React with file-based routing; server functions cover the AI panel and PDF export without a separate backend service.
State Zustand / Jotai Selector-based subscriptions keep scroll updates cheap with many independently-animating components.
Motion Framer Motion (apply layer) + custom phase engine Framer handles GPU-accelerated transform application; the phase/keyframe logic itself is custom, since Framer's built-in scroll triggers assume slide-like, uniform behavior.
Styling Tailwind CSS The most reliable generation target for the AI panel.
AI Anthropic TypeScript SDK, Claude Opus 5 Scoped tool-use loop against a single presentation folder, per §04.
Storage Local filesystem Matches the "presentation is a folder" model directly; swappable for cloud storage later without touching the config schema.
PDF Playwright + pdf-lib Screenshot-per-phase, composed into a PDF, per §07.
Validation Zod One schema shared by the editor, the runtime, and the AI tool-use loop.

09

Studio: many presentations, one app

A workspace root is configured once. The dashboard scans it for presentation folders and lists them; each opens into /studio/:id/edit or /studio/:id/present. Creating a new presentation scaffolds the folder structure from §02 and, optionally, seeds a first pass of components and config straight from one natural-language description.

10

Roadmap

MVP

Prove the feeling is real

Goal: confirm scroll-choreography actually tells a story better than slides, before investing in the editor or AI layer.

  • Zod config schema + the folder structure from §02
  • Phase/keyframe interpolation hook, hand-authored config, 2–3 real components
  • Plain present-mode route — no editor, no AI yet
V1

A usable personal tool

  • Studio dashboard — list and create presentations
  • Visual editor: canvas, phase timeline, properties panel
  • AI generation panel — scoped tools, diff-and-approve flow
  • PDF export
V2

Polish & power

  • Per-keyframe easing curves
  • Asset manager with drag-and-drop import
  • Undo/redo; git-backed history (the folder is already git-friendly)
  • Components with their own internal micro-timelines — e.g. a chart animating its own bars across one phase's scroll range

Deliberately out of scope for now:

  • Multi-user accounts, auth, or hosted sharing links — personal/small-business use for now
  • Branching or non-linear phase graphs — phases stay a single linear track
  • WebGL/3D meshes — CSS transforms cover the spatial storytelling this needs, without the engineering and compositing cost of a second render pipeline

11

Open risks

Performance under many independent components

The selector-based re-render strategy in §03 needs to be proven at MVP, not assumed — it's the one piece of the architecture the whole "independent choreography" premise rests on.

AI-generated component quality

Mitigated by the fixed authoring contract and schema validation in §04 — the plan is to constrain generation tightly rather than trust raw output.

Loading newly-written files without a restart

The AI panel writes new .tsx files at runtime. Picking them up without a full dev-server restart is the single biggest unproven technical step — worth a dedicated spike early, before V1 is scoped in detail.

The config schema will change

Version presentation.json from day one so existing presentations can be migrated forward as the shape evolves.

Draft plan — scope and sequencing to revisit once the MVP in §10 either confirms or kills the core premise.
